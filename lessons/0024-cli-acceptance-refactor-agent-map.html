详细心智模型：从验收证据反推边界

1. 完整检查链由快到慢

export function demoAcceptancePipeline(): string[] {
  return ["validate", "typecheck", "test", "build", "notes --help"];
}

HTML 与链接先失败，随后类型、行为、产物和真实入口。越早的失败越便宜；后一步只在前一步可靠时有意义。

2. 编排依赖能力，不依赖全局进程

export function demoInjectedCapability(): string[] {
  const dependencies = {
    add: "(title) => Promise<Note>",
    list: "() => Promise<readonly Note[]>",
  };
  return Object.keys(dependencies);
}

命令只知道 add/list 能力，不知道 JSON 文件路径、网络或数据库。测试用小 fake，生产入口连接真实 repository。

3. 结构化结果最后才写入进程

export function demoCliResult() {
  return {
    success: { exitCode: 0, stdout: "n1\tDraft\n", stderr: "" },
    empty: { exitCode: 0, stdout: "", stderr: "" },
    failure: { exitCode: 1, stdout: "", stderr: "Error: offline\n" },
  };
}

execute 返回数据，入口再 write 并设置 exitCode。这样成功、空列表和依赖失败都能断言，不需要拦截全局 console。

空列表也是成功

没有数据不是运行失败；脚本可依赖退出码 0。

失败原因进入 stderr

业务结果和诊断不混流，错误文本统一由编排边界规范化。

4. 重构必须保持可观察行为

export function demoSafeRefactorOrder(): string[] {
  return ["green test", "small change", "green test", "full check"];
}

先确认绿色基线，再删除重复或改名。一次改一个边界；若测试同时重写，就失去对行为是否保持的证据。

5. Agent 能力地图从确定性工具开始

export function demoAgentCapabilityMap(): object {
  return {
    read: ["list notes", "load one note"],
    propose: ["summarize", "suggest tags"],
    writeWithApproval: ["add note", "replace note"],
  };
}

读取、建议、写入是不同权限。模型输出仍视作 unknown，经校验后成为命令；有副作用的动作在明确边界执行并留下结果。

完成定义：行为可从公开命令观察，错误不毁数据，测试可复现，构建产物可运行，文档说明的命令与真实 package scripts 一致。

常见误区

  • 入口同时解析、读写、格式化。任何测试都必须启动完整进程。
  • 空列表返回失败。把正常状态误报成异常。
  • catch 后只返回字符串。调用者失去退出码与输出流信息。
  • 为了“架构”新增多层接口。两个函数依赖已足够表达边界。
  • 重构时改变测试期望。无法证明行为保持。
  • 让 Agent 生成任意 shell。应提供窄、验证过、可审计的能力。
  • 只说本地绿色就是发布成功。安装、权限和真实环境仍需独立验收。

你要交付什么

type FinalNoteCommand =
  | { readonly kind: "add"; readonly title: string }
  | { readonly kind: "list"; readonly json: boolean }
  | { readonly kind: "help" };

type CliDependencies = {
  readonly add: (title: string) => Promise<CliNote>;
  readonly list: () => Promise<readonly CliNote[]>;
};

executeNoteCommand(
  command: FinalNoteCommand,
  dependencies: CliDependencies,
): Promise<CliResult>

运行规则

  • help 不调用依赖，stdout 返回三条命令用法并以换行结束。
  • add 调用一次 add，成功输出 Added id: title\n。
  • list --json 输出两空格 JSON 与换行；普通 list 每行 id\ttitle，空列表输出空字符串。
  • 任意依赖失败返回 exitCode 1、空 stdout 与规范化 Error: message\n stderr。
  • 成功 exitCode 为 0 且 stderr 为空。

实现限制

只做命令编排；不要读取 process、文件或 argv，不要引入 class、框架、日志器或 Agent SDK。用 never 保持命令穷尽；Lab 前保留 /** @lab */。

折叠完整答案与逐行解析

显示完整答案
export type CliNote = { readonly id: string; readonly title: string };
export type FinalNoteCommand =
  | { readonly kind: "add"; readonly title: string }
  | { readonly kind: "list"; readonly json: boolean }
  | { readonly kind: "help" };
export type CliDependencies = {
  readonly add: (title: string) => Promise<CliNote>;
  readonly list: () => Promise<readonly CliNote[]>;
};
export type CliResult = {
  readonly exitCode: 0 | 1;
  readonly stdout: string;
  readonly stderr: string;
};

/** @lab */
export async function executeNoteCommand(
  command: FinalNoteCommand,
  dependencies: CliDependencies,
): Promise<CliResult> {
  try {
    if (command.kind === "help") {
      return { exitCode: 0, stdout: "notes add <title>\nnotes list [--json]\nnotes help\n", stderr: "" };
    }
    if (command.kind === "add") {
      const note = await dependencies.add(command.title);
      return { exitCode: 0, stdout: `Added ${note.id}: ${note.title}\n`, stderr: "" };
    }
    if (command.kind === "list") {
      const notes = await dependencies.list();
      const stdout = command.json
        ? `${JSON.stringify(notes, null, 2)}\n`
        : notes.length
          ? `${notes.map((note) => `${note.id}\t${note.title}`).join("\n")}\n`
          : "";
      return { exitCode: 0, stdout, stderr: "" };
    }
    const unexpected: never = command;
    return unexpected;
  } catch (error) {
    const message = error instanceof Error ? error.message : String(error);
    return { exitCode: 1, stdout: "", stderr: `Error: ${message}\n` };
  }
}
类型
命令、能力与进程结果都成为显式契约。
help/add/list
每个分支只调用必要能力并形成稳定文本。
never
新增 kind 时编译器要求更新编排。
catch
依赖失败统一规范化，不触碰全局进程。
